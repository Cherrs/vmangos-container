# vmangos-container

[简体中文](README.zh-CN.md)

A container image for [VMaNGOS](https://github.com/vmangos/core), packaged from the official Development Build Release. GitHub Actions downloads the release, checks its SHA256, tests the image, and publishes it to GHCR. The core is not compiled again here.

The image includes `mangosd`, `realmd`, the extraction tools, default configuration files, SQL migrations, and a fixed four-database snapshot. Supply client files and extracted game data separately.

## Image and versions

```text
ghcr.io/cherrs/vmangos-container:a9fa07a-5875
ghcr.io/cherrs/vmangos-container:sha-<repository-commit>
```

| Setting | Value |
| --- | --- |
| Platform | `linux/amd64` |
| Client | Original WoW 1.12.1, build 5875 |
| Core commit | [`a9fa07aab5e745cae17c5016c9eddffdb75ea7f1`](https://github.com/vmangos/core/tree/a9fa07aab5e745cae17c5016c9eddffdb75ea7f1) |
| Official binary archive | `dev-linux-amd64-a9fa07a.tar.gz` |
| Base image | Ubuntu 24.04, matching the upstream Linux release environment |
| Database used in CI | MariaDB 10.11 |

The release bundles its non-glibc shared libraries and loads them through relative RPATHs. The `a9fa07a-5875` tag can change when this repository's packaging changes. The `sha-...` tag identifies a commit in this repository, not the upstream core. Use the `@sha256:...` reference from the Actions summary to pin the exact published image.

## Pull the image

```bash
docker pull ghcr.io/cherrs/vmangos-container:a9fa07a-5875
```

## Mount game data at /data

These Bash examples assume an initialized database reachable as `vmangos-db` on an existing Docker network named `vmangos`. Both servers use the same database credentials. For a fresh database, run [bootstrap](#initialize-a-fresh-database) first.

Prepare the extracted data on the Docker host:

```text
/srv/vmangos/data/
├── 5875/
│   └── dbc/
├── maps/
├── vmaps/
└── mmaps/
```

Each directory needs files generated by the matching extraction tools. The container runs as UID/GID `10001` and must be able to read the files and traverse the directories. See the [upstream extraction guide](https://vmangos.github.io/wiki/Getting-it-working-Linux/) to prepare the data.

Set the image and database connection in your shell:

```bash
export VMANGOS_IMAGE=ghcr.io/cherrs/vmangos-container:a9fa07a-5875
export DB_HOST=vmangos-db
read -rsp 'Database password: ' DB_PASSWORD; echo
export DB_PASSWORD
```

Start the world server with a read-only bind mount:

```bash
docker run -dit \
  --name vmangos-world \
  --network vmangos \
  --restart unless-stopped \
  --publish 8085:8085 \
  --env DB_HOST --env DB_PASSWORD \
  --mount type=bind,source=/srv/vmangos/data,target=/data,readonly \
  "$VMANGOS_IMAGE" mangosd
```

`/srv/vmangos/data` is the host path; `/data` is the container path. The host directory must already exist. Keep `-it` so the world server's console has an open stdin and TTY.

The login server uses the same image and database, but does not need game data:

```bash
docker run -d \
  --name vmangos-login \
  --network vmangos \
  --restart unless-stopped \
  --publish 3724:3724 \
  --env DB_HOST --env DB_PASSWORD \
  "$VMANGOS_IMAGE" realmd
```

The database's realm address must point to a public IPv4 address or DNS name that clients can reach on port 8085. Open TCP 3724 and 8085 on the host and any upstream firewall. Persist and back up the database independently of the game data directory.

## Initialize a fresh database

The startup wrapper expects the four databases to have been initialized with this image's `bootstrap` command. For an empty database server, set the image and database variables shown above, then run the command below before starting the servers. The database must be reachable on the `vmangos` network, and its root account must allow the connection.

```bash
export PUBLIC_ADDRESS=wow.example.com
read -rsp 'Database root password: ' DB_ROOT_PASSWORD; echo
export DB_ROOT_PASSWORD
docker run --rm --network vmangos \
  --env DB_HOST --env DB_PASSWORD --env DB_ROOT_PASSWORD --env PUBLIC_ADDRESS \
  "$VMANGOS_IMAGE" bootstrap
unset DB_ROOT_PASSWORD
```

Replace `wow.example.com` with your server's address. Bootstrap creates `realmd`, `characters`, `mangos`, and `logs` plus the `mangos` user, imports the snapshot, applies missing migrations, and configures realm ID 1. It does not create player or GM accounts.

Bootstrap refuses to import over existing or partially imported tables. Repeating a completed bootstrap for the same core revision leaves the data and realm settings unchanged. It is not an upgrade command for an existing player database.

## Commands and configuration

| Command | Purpose |
| --- | --- |
| `bootstrap` | Initialize a fresh database and set the realm address |
| `wait` | Wait for a completed bootstrap matching the core revision |
| `realmd` | Generate configuration and start the login server on TCP 3724 |
| `mangosd` | Default command; start the world server on TCP 8085 |

| Environment variable | Purpose |
| --- | --- |
| `DB_HOST` | Database host; defaults to `vmangos-db` |
| `DB_PORT` | Database port; defaults to `3306` |
| `DB_PASSWORD` | Password for the fixed `mangos` database user; 24–128 ASCII letters, digits, or underscores |
| `DB_ROOT_PASSWORD` | Used only by bootstrap to create the databases and user |
| `PUBLIC_ADDRESS` | Required by bootstrap; client-facing IPv4 address or DNS name, up to 32 characters |
| `REALM_NAME` | Realm name used by bootstrap; defaults to `VMaNGOS` |

RA and SOAP are disabled. For a read-only root filesystem, also provide writable mounts at `/run/vmangos`, `/var/log/vmangos`, and `/tmp`; the runtime and log directories must be writable by UID 10001. Logs in the container's writable layer are lost when the container is removed.

## Build and publish

Changes to `image/`, `scripts/`, or the workflow on `main` trigger a build. You can also use **Actions → Build, verify and publish to GHCR → Run workflow**. Pull requests run the checks without logging in to GHCR or publishing. Manual runs on other branches do not publish either.

Before publishing, CI checks the server and extractor library dependencies, imports all four databases into temporary MariaDB storage, repeats bootstrap to check data preservation, renders the configuration, and starts `realmd` with a read-only root filesystem. It pushes that same tested image using `GITHUB_TOKEN` with `contents: read` and `packages: write`. Action versions are pinned to commit SHAs; no long-lived push token is needed.

These checks do not cover extracted map data, in-game login, or world gameplay. CI does not connect to a live game server.

To build and run the checks locally:

```bash
docker build -t vmangos-container:local ./image
bash scripts/smoke-test.sh vmangos-container:local
```

The check script creates and removes the temporary containers `vmangos-ci-db`, `vmangos-ci-login`, and the `vmangos-ci` network. Run one copy at a time. It generates temporary database passwords and masks them in Actions logs.

SQL migrations and the license come from the same core commit. Only those files are extracted from the source archive; its hash is pinned in the [Dockerfile](image/Dockerfile).

Upstream replaces assets in the `latest` and `db_latest` releases, so older download URLs may disappear. Keep your own copy of the release files if you need to rebuild them later, and retain the recorded hashes.

When updating the core, update `CORE_REV`, `RELEASE_ARCHIVE`, both binary and source archive hashes, the workflow's core/client tag, and this version information. Plan database migrations separately. The upstream license is included at `/opt/vmangos/LICENSE`, and the source is available at the pinned commit linked above.
